01. Relational Foundations & Architecture

Beginner to Pro

💡 The Mental Model: Tables as Excel Sheets with Strict Contracts

Imagine an Excel workbook. Each worksheet is a Table. Each horizontal line is a Row (Record) representing one specific entity (like a customer, an order, or a 1-minute stock candle). Each vertical column is a Field (Attribute) with a strict data type (Number, Text, or Date).

Unlike an Excel spreadsheet where you can type anything anywhere, a Relational Database guarantees Integrity: a price column will never accidentally contain a letter, and every row can be uniquely identified.

🏛️
The 4 SQL Dialect Families:
• DQL (Query): SELECT — Asking questions and viewing data without changing it.
• DML (Manipulation): INSERT, UPDATE, DELETE — Adding, altering, or removing rows.
• DDL (Definition): CREATE, ALTER, DROP — Creating or altering the table structures.
• TCL (Control): COMMIT, ROLLBACK — Managing transactional checkpoints and safety.

⚡ The Golden Secret: How SQL Actually Runs (Execution Order)

Most beginners struggle with SQL because the order you write SQL is NOT the order the database executes it!

You start your query with SELECT, but the database actually executes SELECT near the very end. This is why you cannot use a column alias defined in SELECT inside your WHERE clause!

02. Querying & Filtering (DQL)

Core Retrieval

1. Basic SELECT, Column Aliasing & DISTINCT

The SELECT statement extracts columns from a table. Use an alias (AS) to give columns human-friendly labels. Use DISTINCT when you want to remove duplicate rows from your output.

📄 SQL Example 
-- Select unique symbols and compute spread from market candles
SELECT 
    symbol,
    close,
    open,
    (high - low) AS candle_range,
    volume
FROM candles
WHERE volume > 1000
LIMIT 5;
💡
Production Best Practice: Avoid SELECT * in production pipelines! Always explicitly type the column names you need. This saves memory, reduces disk I/O, and avoids application breaks when new columns are added.

2. Filtering: WHERE, Pattern Matching (LIKE), IN & BETWEEN

The WHERE clause acts as a bouncer at the door, evaluating row-by-row:

  • =, != (or <>), <, >, <=, >=: Standard comparisons.
  • IN ('NIFTY', 'BANKNIFTY'): Checks if a value belongs to an explicit list.
  • BETWEEN 100 AND 500: Inclusive boundary range check.
  • LIKE '%TECH%': Wildcard text matching (% matches any sequence of characters, _ matches exactly one character).
📄 Advanced Filtering 
-- Find all trades where symbol starts with 'RELIANCE' or is in specific list
SELECT trade_id, symbol, side, price, qty, (price * qty) AS total_val
FROM trades
WHERE (symbol LIKE '%NIFTY%' OR symbol IN ('TCS', 'INFY'))
  AND price BETWEEN 1500 AND 3500
ORDER BY price DESC;

3. Sorting & Pagination: ORDER BY, LIMIT & OFFSET

By default, relational databases make zero guarantee about the order rows are returned unless you explicitly specify ORDER BY.

Use ASC (default, lowest first) or DESC (highest first). Use LIMIT and OFFSET to build clean paginated APIs (e.g. Page 2 with 10 items: LIMIT 10 OFFSET 10).

📄 Sorting & Pagination 
-- Top 3 highest volume candles for NIFTY
SELECT symbol, datetime, close, volume
FROM candles
WHERE symbol = 'NIFTY'
ORDER BY volume DESC
LIMIT 3;

03. Mutation (DML) & Table Schema (DDL)

Writing Data

1. INSERT, UPDATE & DELETE (With Crucial Safeguards)

Manipulating existing data requires extreme care. An UPDATE or DELETE without a WHERE clause will permanently modify or wipe the entire table!

⚠️
Junior Mistake to Avoid:
Running UPDATE accounts SET balance = 0; will set every single customer's balance to 0! Always test your condition first with SELECT * FROM accounts WHERE ... before converting it to an UPDATE or DELETE.
📄 Safe Mutation Workflow 
-- 1. Insert a new execution order
INSERT INTO trades (symbol, side, price, qty, timestamp)
VALUES ('NIFTY', 'BUY', 24500.50, 50, '2026-09-18 09:15:00');

-- 2. Verify the inserted row immediately
SELECT * FROM trades WHERE symbol = 'NIFTY' ORDER BY trade_id DESC LIMIT 1;

2. CREATE TABLE & Constraint Architecture

Constraints are rules enforced by the database engine at write-time. If an incoming row breaks any rule, the database aborts the transaction.

  • PRIMARY KEY: Uniquely identifies each record. Always mandatory on production tables.
  • FOREIGN KEY: Enforces referential integrity pointing to a primary key in another table.
  • NOT NULL: Disallows missing values.
  • UNIQUE: Guarantees no two rows have the same value for this column.
  • CHECK: Custom boolean condition (e.g. CHECK (price > 0)).
  • DEFAULT: Automatically fills a value when omitted.
📄 Production Schema Design 
-- Designing a resilient Trade Ledger table
CREATE TABLE IF NOT EXISTS execution_logs (
    log_id INTEGER PRIMARY KEY AUTOINCREMENT,
    order_ref TEXT NOT NULL UNIQUE,
    symbol TEXT NOT NULL,
    executed_price REAL NOT NULL CHECK (executed_price > 0),
    filled_qty INTEGER NOT NULL CHECK (filled_qty > 0),
    status TEXT DEFAULT 'FILLED',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- Inspect schema via SQLite master
SELECT name, sql FROM sqlite_master WHERE type='table' AND name='execution_logs';

04. Relational Joins & Set Operations

Relational Power

🎨 Interactive JOIN Visualizer (Venn Diagram + Result Set)

Joins combine columns from two or more tables based on a related column between them. Click the buttons below to visually see which rows are included and where NULL values are produced:

INNER JOIN: Returns only rows where there is a matching key in BOTH tables. Customers without orders and orders without customers are excluded.

Real-World Join Example: Customers & Their Orders

In analytics, we often want all customers along with their total order values—even if a customer hasn't placed any orders yet. This is the prime use-case for a LEFT JOIN.

📄 Multi-Table Join 
-- Show customer details alongside their order stats (LEFT JOIN preserves all customers)
SELECT 
    c.customer_id,
    c.name AS customer_name,
    c.city,
    o.order_id,
    o.item_name,
    o.amount
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
ORDER BY c.customer_id ASC;

Set Operations: UNION vs UNION ALL

While JOIN merges tables horizontally (adding columns), UNION stacks results vertically (adding rows).

• UNION: Combines datasets and sorts them to remove duplicate rows (higher CPU overhead).
• UNION ALL: Combines datasets quickly without deduplication (much faster).

📄 UNION ALL Stack 
-- Combine equity buy actions and equity sell actions into a unified stream
SELECT trade_id, symbol, 'BUY_ORDER' AS order_category, price FROM trades WHERE side = 'BUY'
UNION ALL
SELECT trade_id, symbol, 'SELL_ORDER' AS order_category, price FROM trades WHERE side = 'SELL'
ORDER BY trade_id ASC
LIMIT 5;

05. Aggregation, Grouping & Summaries

Analytics Core

1. Aggregate Functions (COUNT, SUM, AVG, MIN, MAX)

Aggregate functions take multiple row values and boil them down into a single summary scalar value.

  • COUNT(*): Counts total rows including NULLs.
  • COUNT(column): Counts non-null entries in that column.
  • COUNT(DISTINCT column): Counts unique occurrences.
  • SUM(col), AVG(col), MIN(col), MAX(col): Numerical reductions.

2. GROUP BY and the Crucial Difference Between WHERE and HAVING

GROUP BY splits rows into distinct buckets based on matching values in the specified columns.

🎯
Rule of Thumb:
• WHERE filters individual raw rows before any grouping happens.
• HAVING filters aggregated summary buckets after groups have been computed.
📄 Aggregation with HAVING 
-- Group trades by symbol and filter symbols with total volume > 500
SELECT 
    symbol,
    COUNT(*) AS total_trades,
    SUM(qty) AS total_quantity,
    ROUND(AVG(price), 2) AS avg_fill_price,
    MIN(price) AS lowest_price,
    MAX(price) AS highest_price
FROM trades
WHERE price > 0
GROUP BY symbol
HAVING total_quantity > 100
ORDER BY total_quantity DESC;

06. Advanced Analytics & Modern SQL

Senior Level

1. Window Functions (OVER, PARTITION BY, ORDER BY)

Unlike GROUP BY which collapses multiple rows into one, Window Functions perform calculations across a set of table rows while still retaining each individual row's identity!

Key Window Functions: ROW_NUMBER() (sequential 1,2,3), RANK() (ties share rank, skips numbers), DENSE_RANK() (ties share rank, no skips), LAG() (peek at previous row), LEAD() (peek at next row).

📄 Running Totals & Ranks 
-- Compute running cumulative volume and rank orders per symbol
SELECT 
    trade_id,
    symbol,
    price,
    qty,
    ROW_NUMBER() OVER (PARTITION BY symbol ORDER BY price DESC) AS price_rank_in_symbol,
    SUM(qty) OVER (PARTITION BY symbol ORDER BY trade_id ASC) AS cumulative_volume,
    LAG(price, 1) OVER (PARTITION BY symbol ORDER BY trade_id ASC) AS previous_trade_price
FROM trades
ORDER BY symbol, trade_id;

2. Common Table Expressions (CTEs with WITH)

Subqueries can quickly turn into messy, unreadable "SQL spaghetti". CTEs (Common Table Expressions) let you define named temporary result sets before your main query, reading like clean, sequential paragraphs.

📄 Clean CTE Pipeline 
-- Find all customers who have spent more than the average order total
WITH customer_spending AS (
    SELECT 
        customer_id,
        SUM(amount) AS total_spent
    FROM orders
    GROUP BY customer_id
),
spending_benchmark AS (
    SELECT AVG(total_spent) AS overall_avg FROM customer_spending
)
SELECT 
    c.name,
    cs.total_spent,
    ROUND(b.overall_avg, 2) AS benchmark_avg
FROM customer_spending cs
JOIN customers c ON cs.customer_id = c.customer_id
CROSS JOIN spending_benchmark b
WHERE cs.total_spent > b.overall_avg;

3. Conditional Logic (CASE WHEN) & Date Manipulation

CASE WHEN provides the equivalent of if-else branching inside SQL. It allows you to create categorical labels, risk tiers, or conditional aggregations on the fly.

📄 CASE WHEN Logic 
-- Categorize trades into sizing tiers and check price change direction
SELECT 
    trade_id,
    symbol,
    qty,
    CASE 
        WHEN qty >= 100 THEN 'Institutional Block'
        WHEN qty >= 40  THEN 'Mid-tier Lot'
        ELSE 'Retail Size'
    END AS order_bracket,
    price
FROM trades
ORDER BY qty DESC;

4. Financial & Trading Analytics (Moving Averages & Breakouts)

In algorithmic trading and financial databases (like your market_data.db), we frequently calculate Simple Moving Averages (SMA), Highest Highs, and Price Changes over rolling candle windows.

📄 Moving Average & Volatility 
-- Calculate a 3-period Rolling Simple Moving Average (SMA-3) and Momentum on Candles
SELECT 
    datetime,
    symbol,
    close,
    ROUND(AVG(close) OVER (
        PARTITION BY symbol 
        ORDER BY datetime 
        ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
    ), 2) AS sma_3_period,
    MAX(high) OVER (
        PARTITION BY symbol 
        ORDER BY datetime 
        ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
    ) AS rolling_high
FROM candles
WHERE symbol = 'NIFTY'
ORDER BY datetime ASC;

07. Indexing, Performance & Transactions

Production Ready

1. How Indexes Work & Reading EXPLAIN QUERY PLAN

Without an index, searching for a symbol in a 10-million row database requires a Full Table Scan (checking every single row from beginning to end). An Index (B-Tree) works like the index at the back of a textbook: it allows the database to locate exact rows in logarithmic time O(log N).

Use EXPLAIN QUERY PLAN before any query to see whether SQLite is performing a fast SEARCH TABLE USING INDEX or a slow SCAN TABLE.

📄 Index Inspection 
-- 1. Create an index on symbol and datetime for high-speed candle lookups
CREATE INDEX IF NOT EXISTS idx_candles_sym_time 
ON candles (symbol, datetime);

-- 2. Inspect query execution strategy
EXPLAIN QUERY PLAN 
SELECT * FROM candles 
WHERE symbol = 'NIFTY' AND datetime > '2026-09-18';

2. ACID Transactions (BEGIN, COMMIT, ROLLBACK)

Imagine transferring ₹10,000 from Account A to Account B. If power fails after debiting Account A but before crediting Account B, your money vanishes!

Transactions guarantee Atomicity (All-or-Nothing). Either all queries inside the transaction succeed, or the entire operation is rolled back as if nothing happened.

📄 Atomic Transaction Example 
-- Safe multi-step execution block
BEGIN TRANSACTION;

INSERT INTO trades (symbol, side, price, qty, timestamp)
VALUES ('BANKNIFTY', 'BUY', 52100.00, 30, '2026-09-18 10:00:00');

-- Commit all changes safely to disk
COMMIT;

SELECT * FROM trades WHERE symbol = 'BANKNIFTY';
🎯 Hands-On Challenge
Challenge: Write a query to find the single most traded symbol in the trades table by total rupee value (Price × Quantity). Return the symbol and the total turnover formatted to 2 decimals.
💡 Solution Query 
SELECT 
    symbol,
    ROUND(SUM(price * qty), 2) AS total_turnover
FROM trades
GROUP BY symbol
ORDER BY total_turnover DESC
LIMIT 1;
